# 配布・バージョン管理の方針

- 決定日: 2026-10-10
- 状態: 採用（実装中）

この文書は「Rust 環境が無い PC にも簡単にインストールでき、バージョンアップも
容易にする」ために決めた方針と、**なぜそう決めたか**を残すためのもの。
後から方針を変えるときは、この文書の該当箇所を更新し、変更理由を末尾の
「変更履歴」に追記すること。

## 背景（決定時点の状態）

決定時点（2026-10-10）では、本ソフトは「リポジトリを clone し、その場で
`cargo build --release` して動かす」前提で作られていた。具体的には:

| 項目 | 決定時点の挙動 | 別 PC で困ること |
|---|---|---|
| 辞書（`dictionaries/system.dic` 等） | カレントディレクトリ基準で探す | 起動場所次第で見つからない |
| 学習 DB（`ime-learning.db`） | カレントディレクトリに作る | `C:\Program Files` 等では書き込めない |
| ログ（`hook_debug.log` / `hook_latency.log` / `hook_watchdog.log`） | `C:\Projects\ime-live-converter\` に**ハードコード** | そのフォルダが無い PC では書けない |
| 起動（`run-hidden.vbs`）・自動起動登録（`install-autostart.ps1`） | `target\release\conversion-service.exe` を直接指す | ビルドしていない PC には存在しない |
| 判断層モデル（`judge_lm.bin` 260MB / `judge_cooc.bin` 111MB） | Git 管理外。Wikipedia から手元で数時間かけて生成 | CI で毎回作れない |
| バージョン | 全 crate が `0.1.0` のまま、タグ無し | どの版で起きた不具合か分からない |

## 決定事項

### 1. バージョン番号はセマンティックバージョニング（MAJOR.MINOR.PATCH）

| 変更の種類 | 上げる桁 | 例 |
|---|---|---|
| バグ修正・誤変換の修正（挙動の意図は変えない） | PATCH | 1.0.0 → 1.0.1 |
| 機能追加・既定の挙動が目に見えて変わる変更 | MINOR | 1.0.1 → 1.1.0 |
| 互換性が切れる変更（学習 DB・設定を自動で引き継げない、インストール先の変更等） | MAJOR | 1.x → 2.0.0 |

**理由**: 「改修はすべて 1.0.1, 1.0.2…と PATCH で上げる」案も検討した。動作上は
問題ないが、番号から「バグ修正だけの更新か、挙動が大きく変わる更新か」が
読み取れなくなる。IME は日常の入力そのものなので、利用者が「この更新は入れて
大丈夫か」「不具合はどの版から出たか」を番号だけで判断できる方が価値が高い。
MAJOR を「データを引き継げない」に限定したのは、利用者にとって最も痛いのが
学習内容の喪失だから。

### 2. 1.0.0 は「別 PC にインストールできる最初の版」に付ける

**理由**: 決定時点のコードをそのまま 1.0.0 にする案もあったが、上の表の通り
決定時点のコードは別 PC では動かない。「1.0.0 = 配布物として成立した最初の版」
とした方が、番号の意味（ここから互換性を守る）と実態が一致する。
手順は「未コミットの修正を確定 → `feature/judge-lm` を master に取り込み →
下記 3〜5 の改修 → 別環境で動作確認 → `v1.0.0` タグ」。

### 3. バージョンの正本は `Cargo.toml` の `[workspace.package] version` 1 か所

各 crate は `version.workspace = true` で参照する。リリースは git タグ `vX.Y.Z` で
行い、CI はタグと `Cargo.toml` の版が一致しない場合は失敗させる。
アプリは版を表示し（設定画面・起動ログ）、不具合報告で版が分かるようにする。

**理由**: 版の記述が複数箇所にあると必ずずれる（決定時点で 6 か所に `0.1.0`
が散在していた）。タグと照合すれば「タグを打ったのに版を上げ忘れた」を機械的に防げる。

### 4. ファイルの置き場所を「プログラム」と「ユーザーデータ」に分ける

| 種類 | 置き場所 | 更新時 |
|---|---|---|
| プログラム（exe / DLL / スクリプト） | インストール先（既定 `%LOCALAPPDATA%\Programs\IMELiveConverter\`） | 上書き |
| 同梱データ（辞書・判断層モデル・`word_priority.tsv` 等） | インストール先の `dictionaries\`（exe の隣を基準に探す） | 版が変わったときだけ上書き |
| ユーザーデータ（学習 DB・ログ・設定） | `%LOCALAPPDATA%\IMELiveConverter\` | **触らない** |

開発時（リポジトリ内で `cargo run` する場合）は従来どおり動くよう、探索順は
「exe の隣 → カレントディレクトリ」とする。開発環境の既存 `ime-learning.db` は、
新しい場所に学習 DB が無いときに一度だけ移行（コピー）する。

**理由**:
- 更新でプログラムを丸ごと置き換えても学習内容が消えないようにするため
  （学習の喪失が利用者にとって最大の損失）。
- `C:\Program Files` はユーザー権限で書き込めないため、学習 DB をプログラムと
  同じ場所に置く設計はインストール型配布と両立しない。
- インストール先を `Program Files` ではなく `%LOCALAPPDATA%\Programs` にするのは、
  インストール・更新に管理者権限を要らなくするため（VS Code 等のユーザー単位
  インストールと同じ考え方）。ただし自動起動タスクを「最上位の権限」で登録する
  ため、その登録時だけは管理者権限が要る（下記 7）。

### 5. 配布物は「本体」と「モデル」を分ける

- 本体パッケージ（数 MB）: exe / DLL / 小さな同梱データ / インストールスクリプト
- モデル（約 370MB）: `system.dic` / `judge_lm.bin` / `judge_cooc.bin`。
  モデルには独自のバージョン（`packaging/models-version.txt`、例: `models-2026.10.10`）を付け、
  本体の版とは独立させる。同名の GitHub Release に**ファイルを個別に**
  （ZIP にまとめずに）`SHA256SUMS.txt` と一緒に置く。個別にしたのは、CI のテストが
  `system.dic`（5.5MB）だけを取得すれば済むようにするため。モデルのリリースは
  一度公開したら差し替えない（中身を変えるときは版を上げる）

**理由**: ほとんどの改修（誤変換修正など）はプログラムだけの変更で、モデルは
変わらない。毎回 370MB を配り直すと更新が重くなり、「更新が面倒だから古い版の
まま」になりやすい。分けておけば通常の更新は数 MB で済む。
モデルは Wikipedia から数時間かけて生成するため CI では作らず、手元で生成した
ものを GitHub Release の添付ファイル（1 ファイル 2GB まで可）として置き、
CI はそれを取り込む。Git LFS も検討したが、無料枠（容量・帯域）がモデルの
大きさに対して小さく、更新のたびに枠を消費するため採らない。

`system.dic` は小さいので本体側に入れる（CI で IPA 辞書から作る）ことも検討したが、
実装時（2026-10-10）に試したところ、**今の dict-builder で作り直した辞書は手元の
`system.dic` と一致しなかった**（カタカナ語のコスト補正値が違い、手元の方が 213 語多い。
過去の作り方の履歴が残っていない）。作り直した辞書に替えると、ゴールデンテストで
調整してきた変換結果が変わるため、`system.dic` も手元のものをモデルとして配る。
`extra.csv` を変えて辞書を作り直したときは、モデルの版を上げて配り直す。

### 6. 学習 DB にスキーマの版を持たせる

SQLite の `PRAGMA user_version` に版を記録し、起動時に古い版なら順番に変換
（マイグレーション）を適用する。

**理由**: 決定時点では列の追加を「`ALTER TABLE` を毎回試して失敗は無視」で
処理していた。列の追加はそれで足りるが、表の作り直しや値の変換が必要に
なった時点で破綻する。版番号があれば、どの順で何を適用するかが明確になり、
更新で学習 DB を壊さない（＝MAJOR を上げずに済む）範囲が広がる。

### 7. 更新は同じインストールスクリプトで行う

`install.ps1` は新規インストールと更新を兼ねる: 動作中の `conversion-service.exe`
を停止 → プログラムを置き換え → （必要なら）モデルを置き換え → 自動起動タスクを
登録し直す → 起動。アンインストール用 `uninstall.ps1` も同梱し、ユーザーデータは
既定で残す（消すかは確認する）。

**理由**: 「入れ方」と「上げ方」が別手順だと、更新手順の方が使われずに
腐りやすい。1 本にしておけば常に同じ経路が使われ、テストもされる。
アプリ内の自動更新（自分で自分を書き換える）は採らない。キーボードフックを
持つ常駐プロセスが自身を差し替えるのは失敗時に入力ができなくなる危険があり、
得られる手間の削減に見合わない。代わりに、将来「新しい版がある」ことを
通知するだけの機能は追加してよい。

### 8. リリースは GitHub Actions でタグから自動作成

`vX.Y.Z` タグの push で、Windows ランナー上で
テスト（`scripts/run-tests.ps1`）→ リリースビルド → パッケージ作成 →
GitHub Release に公開、を行う。バイナリは C ランタイムを静的リンク
（`crt-static`）し、Visual C++ 再頒布可能パッケージの無い PC でも動くようにする。

**理由**: 手作業のリリースは手順漏れ（テスト未実行・ファイルの入れ忘れ）が
起きる。タグを起点にすれば「タグ = テスト済みの配布物」が保証される。

## 実装（2026-10-10）

| 方針 | 実装 |
|---|---|
| 1, 3 版の付け方・正本 | `Cargo.toml` の `[workspace.package] version`（各 crate は `version.workspace = true`）。`conversion-service.exe --version`、起動ログ、コマンド設定画面のタイトルに表示 |
| 4 置き場所 | `crates/common/src/paths.rs`。学習DBは `LearningRepository::open_default()`（無ければ起動フォルダ・exe の隣の旧DBを `VACUUM INTO` で移行。移行元は消さない）。`IME_DATA_DIR` で上書き可 |
| 5 本体とモデル | `scripts/package.ps1`（`-Models` でモデルも）、`scripts/publish-models.ps1`、`packaging/models-version.txt` |
| 6 スキーマの版 | `learning.rs` の `SCHEMA_VERSION` と `migrate()`。新しい版の DB は開かない |
| 7 インストール・更新 | `packaging/install.ps1` / `uninstall.ps1` / `run-hidden.vbs`（配布物の直下に入る） |
| 8 CI | `.github/workflows/release.yml`（タグ）、`ci.yml`（master への push・PR）。C ランタイムの静的リンクは `.cargo/config.toml` |

### リリース手順

**通常の改修（本体だけ）**
1. 改修をコミットし、`scripts/run-tests.ps1` が通ることを確認する
2. `Cargo.toml` の `[workspace.package] version` を上げる（上の表に従う）
3. `git tag vX.Y.Z` → `git push origin master vX.Y.Z`
4. CI が テスト → パッケージ作成 → GitHub Release 公開 まで行う
5. 利用者は新しい ZIP を展開して `install.ps1` を実行する（学習は残る）

**モデルを変えたとき（辞書の作り直し・判断層の再学習）**
1. `packaging/models-version.txt` を新しい版（例: `models-2026.11.01`）にする
2. `scripts/package.ps1 -Models` → `scripts/publish-models.ps1`
3. 本体の版を上げてリリースする（上の手順）。`install.ps1` は必要なモデルの版が
   入っていなければ自動で取得する

### 開発環境から移るとき

開発用のビルド（`scripts/rebuild-and-run.ps1`、リポジトリ直下で起動）も
1.0.0 以降は `%LOCALAPPDATA%\IMELiveConverter` の学習DB・ログを使う。初回起動時に
リポジトリ直下の `ime-learning.db` が自動で移行される（元のファイルは残る）。
インストール版を先に入れる場合は `install.ps1 -ImportLearningDb <リポジトリ>\ime-learning.db`
で取り込める。

### 手元で確認済み / 未確認

- 確認済み: パッケージ作成、静的リンク（`VCRUNTIME140.dll` への依存が消えた）、
  作業用フォルダへのインストール・更新（版の検出、モデルの再取得をしない）・
  チェックサム不一致の検出・アンインストール、インストール先の辞書・DLL を読んで常駐すること
- 未確認: 管理者権限への昇格と自動起動タスクの登録、GitHub からのモデル取得、
  CI（モデルのリリースを公開するまで動かない）、Rust の無いまっさらな PC での動作

## 決定時点で認識しているリスク・未決事項

- **ウイルス対策ソフト・SmartScreen**: 全キー入力を拾うキーボードフックは
  キーロガーと同じ仕組みのため、署名の無い exe は警告・隔離される可能性がある。
  自分の PC 以外へ広く配る場合はコード署名証明書の取得を検討する。
- **再配布の条件**: IPA 辞書はライセンス表記の同梱で再配布可能。Wikipedia
  由来の判断層モデルは 2026-10-11 に下記「モデルのライセンス」のとおり決定した。
- **インストーラー形式**: まずは ZIP + `install.ps1` とする。MSI / Inno Setup 等の
  「ダブルクリックで入る」形式は、上記が安定してから検討する。

## モデルのライセンス（2026-10-11 決定）

判断層モデル（`judge_lm.bin` / `judge_cooc.bin`）は **CC BY-SA 4.0** として公開する。

- **理由**: モデルは Wikipedia 本文（CC BY-SA 4.0）から作った単語 n-gram・共起の
  集計値で、本文そのものは含まない。集計値が元の文章の「改変物」にあたるかは
  線引きがはっきりしないため、安全側に倒して改変物として扱い、元と同じ条件で配る。
- **帰属表示**: 出典（日本語 Wikipedia、Wikipedia の寄稿者）、ライセンスと URL、
  加えた変更（集計値への縮約）を `packaging/licenses/NOTICE.txt` に書く。
  モデルはプログラムと別の Release で配るため、モデルの Release にも
  `NOTICE.txt` と `IPADIC-COPYING.txt` を添付する（`package.ps1 -Models` が同梱）。
- **本体への影響**: 継承（SA）はモデルのファイルにかかり、それを読み込むだけの
  プログラム本体には及ばないと判断し、本体は MIT のままとする。モデルを本体と
  別の配布物にしている（決定 5）ことも、この切り分けを分かりやすくしている。
- 法律の専門家の確認は受けていない。商用配布など慎重さが要る場面では再確認する。
